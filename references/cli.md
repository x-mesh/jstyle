# CLI와 터미널 출력

명령의 결과, 진행 표시, 도움말, 다음 행동 안내를 다룹니다. 전체 화면을 그리는 TUI도 같은 원칙을 따릅니다.
목표는 사용자가 출력을 다시 읽지 않고 결과와 다음 행동을 아는 것입니다. 사람과 스크립트·에이전트가 모두 같은 명령을 씁니다.

## 범위와 찾기

사용자가 CLI를 말했거나 프로젝트 전체의 스타일 통일을 부탁했을 때만 CLI를 고칩니다. 웹 작업에서 CLI로 넓히지 않습니다.
고칠 곳은 다음 순서로 찾습니다.

- 진입점: `package.json`의 `bin`, `pyproject.toml`의 `[project.scripts]`, Go의 `cmd/`, Rust의 `src/bin/`.
- 출력 라이브러리: `chalk`, `picocolors`, `rich`, `click`, `lipgloss`, `fatih/color` 등을 쓰는 파일.
- 출력 스타일을 모은 모듈: 색·성공 줄·힌트를 만드는 함수가 이미 있으면 그 함수를 따르고 넓힙니다.

기존 모듈이 없을 때만 아래 기본을 씁니다. 출력 문구를 테스트가 비교한다면 함께 고칩니다.
명령 코드에서 색과 들여쓰기를 직접 만들지 않습니다. 출력 모듈에 함수를 더하고 명령은 그 함수를 부릅니다.

## 기본 원칙

- 색은 거들기만 합니다. 상태는 `✓` `!` `✗` 같은 기호와 문구로도 구분되어야 합니다.
- 작업을 멈추는 실패는 그 자리에서 보여 주고, 마지막 요약에서는 실패와 그 영향을 성공보다 먼저 씁니다. 성공은 `✓ <동사> <대상>` 한 줄로 짧게 씁니다.
- 성공해도 아무것도 출력하지 않는 명령은 고장 난 것처럼 보입니다. 짧게 확인하고, 조용히 하려면 `-q`를 줍니다.
- 바뀐 것이 없으면 바뀌었다고 쓰지 않습니다. 인자로 받지 않은 파일을 쓰거나 원격에 접속하면 그 사실을 알립니다.
- 지금 다루는 대상과 단계를 한 줄에서 알아볼 수 있게 합니다. 여러 대상을 함께 돌리면 대상·단계를 같은 열에 맞춥니다.
- 1초 넘게 걸리는 작업은 진행을 보여 줍니다. 상세 정보는 `-v`나 하위 명령으로 요청할 때 보여 줍니다.
- 한 출력 안에서는 한 언어를 씁니다. 영어 메시지 사이에 한국어 한 줄이 섞이지 않게 합니다.
- 시작 배너·로고·박스·장식 애니메이션과 이모지는 기본으로 쓰지 않습니다. 사용자가 켜는 화면에서만 씁니다.

## 출력 모드

모드는 진입점에서 한 번 정하고 출력 함수에 넘깁니다. 명령마다 따로 판단하지 않습니다. 먼저 맞는 조건이 이깁니다.

1. `--json` 같은 기계용 형식: 색·애니메이션·질문을 모두 끕니다.
2. `--no-color`, 그다음 `FORCE_COLOR`, 그다음 비어 있지 않은 `NO_COLOR`: 색만 켜고 끕니다.
3. `TERM=dumb`: 색과 애니메이션을 끕니다. `CI`가 있으면 질문하지 않습니다.
4. 그 밖에는 각 스트림이 TTY인지 따로 봅니다.

stdout이 파이프여도 stderr는 터미널일 수 있습니다. 스피너와 진행 줄은 stderr가 TTY일 때만 씁니다.
stderr가 파이프면 경고와 오류만 보냅니다. 질문은 stdin과 질문을 쓰는 스트림이 모두 TTY일 때만 합니다.

## 색의 역할

| 역할 | 색 | 쓰는 곳 |
|---|---|---|
| 보조 | 회색(dim) | 라벨, `:` 같은 구분자, 표 머리글, 괄호 속 부가 정보 |
| 명령 | cyan | 그대로 복사해 실행할 수 있는 명령 |
| 성공 | 초록 | `✓`와 방금 바뀐 대상 |
| 주의 | 노랑 | 사용자가 판단하거나 손대야 하는 일, 기준을 넘은 값 |
| 실패 | 빨강 | 실패와 기준을 크게 넘은 값 |
| 제목 | 굵게 또는 한 가지 강조색 | 섹션 제목 |

정상 값과 단순한 정보는 기본색으로 둡니다. 모든 값을 초록으로 칠하면 주의와 실패가 묻힙니다.
16색 안에서 뜻이 통하게 고릅니다. 사용자가 터미널 색을 바꿔도 읽혀야 하므로 기울임과 256색에 기대지 않습니다.
문장 전체를 회색으로 감싸고 그 안의 값만 칠할 때는 값 뒤의 글자가 다시 회색이 되는지 봅니다.

## 구조

여러 묶음을 보여 줄 때는 한 칸짜리 막대 머리를 씁니다. 제목과 본문을 같은 열에 맞춥니다.

```text
█  BRANCH
   develop ← main · 14h ago

█  NEXT   → git push -u origin develop
   why: no upstream configured
```

계층이 실제로 있는 자료에만 `├──` `└──` 나무를 씁니다. 가지는 회색입니다.
제목 앞에 이모지를 두지 않습니다. 터미널마다 차지하는 폭이 달라 열이 어긋납니다.
표는 열 사이를 공백 두 칸으로 맞추고 마지막 열은 채우지 않습니다.

여러 대상을 처리할 때 멈추지 않는 경고는 그 자리에서 줄마다 찍지 않습니다. 모아서 종류별로 묶어 마지막 요약 바로 위에 둡니다.
경고에는 사용자가 할 일을 씁니다. 할 일이 없으면 경고가 아니므로 `-v`로 내리거나 지웁니다.

```text
✓ api       3 files
✓ web       1 file

!  2 files skipped: local copy exists
   try: tool sync --force

✓ synced 2 packages
```

## 폭과 식별자

폭은 색을 입히기 전의 글자로 재고, 한글·이모지처럼 두 칸을 차지하는 글자를 셉니다. 자를 때는 글자 단위가 아닌 보이는 글자 묶음 단위로 자릅니다.
색을 쓰는 터미널에서 줄이 넘치면 `…`로 자르거나 다음 항목부터 들여 쓴 새 줄로 넘깁니다. 평문 출력은 자르지 않습니다.
run ID·브랜치·경로·서비스 이름처럼 사용자가 다음 명령에 넣는 값은 자르지 않습니다. 표가 넓으면 다른 열을 줄입니다.

## 입력과 확인

모든 질문에는 같은 일을 하는 옵션이 있어야 합니다. 확인은 `--yes`, 선택과 입력은 `--name=value`처럼 줍니다.
질문할 수 없는 환경에서는 기다리지 않고, 필요한 옵션을 알려 주며 실패합니다.
확인의 무게는 위험에 맞춥니다. 가벼운 변경은 `y/N`, 큰 변경은 `--dry-run`을 먼저 권하고, 되돌릴 수 없는 삭제는 대상 이름을 입력하게 합니다.
비밀번호와 토큰을 옵션 값으로 받지 않습니다. 셸 기록과 프로세스 목록에 남습니다. 파일이나 stdin으로 받습니다.

## 다음 행동과 오류

명령이 끝난 뒤 할 일이 있으면 `next:` `hint:` `try:` 라벨 뒤에 실제 명령을 씁니다.
라벨은 회색, 명령은 cyan, 끝의 `(설명)`은 회색입니다. 명령이 아닌 조언은 라벨만 회색으로 두고 문장은 기본색입니다.
오류에는 실패한 대상, 원인, 고칠 명령을 이 순서로 씁니다. 원인을 모르면 모른다고 씁니다.
명령 이름을 잘못 쳤으면 가장 가까운 이름을 제안합니다. 같은 모양의 오류가 여럿이면 한 머리 아래 묶고 개수를 씁니다.

종료 코드는 성공 0, 작업 실패 1, 잘못된 사용법 2를 기본으로 하고, Ctrl+C로 멈추면 130을 씁니다.
0이 아닌 코드에는 반드시 stderr에 이유를 남깁니다. 따로 정한 코드는 도움말에 적습니다.

## 도움말

첫 줄에 이름·버전·한 줄 설명을 두고, 그 아래에 `usage` 한 줄을 둡니다.
명령은 사용자의 목적별로 묶고, 각 명령을 한 줄로 설명합니다. 이름 열을 맞춥니다.
필수 인자는 `<name>`, 선택은 `[name]`, 반복은 `name...`으로 씁니다. 자주 쓰는 예시를 한두 개 둡니다.
공통 옵션은 마지막에 한 번만 보여 줍니다. 모든 하위 명령에 `--help`가 있어야 합니다.

## 기계용 출력

사람용 출력과 별도로 `--json`처럼 고정된 형식을 줍니다. 사람용 문구를 기계가 읽게 하지 않습니다.
결과는 stdout, 진행·경고·힌트는 stderr로 보내 파이프에 섞이지 않게 합니다.
성공·중단·실패를 구분하는 필드와 다음 명령 목록을 함께 주면 에이전트가 문구를 해석하지 않아도 됩니다.
오류도 같은 형식으로 냅니다. 오류 코드, 메시지, 고칠 방법을 필드로 줍니다.
긴 목록과 로그는 앞부분만 주고 전체 개수와 전체 내용을 담은 파일 경로를 함께 줍니다.
JSON 필드·옵션 이름·종료 코드는 약속입니다. 이름을 바꾸지 말고 새 필드를 더하며, 없애기 전에는 stderr로 미리 알립니다. 사람용 문구는 약속이 아닙니다.

## TUI

80×24와 16색에서 먼저 동작하게 만들고, 그보다 좋은 터미널의 기능은 덧붙입니다.
최소 크기보다 작으면 깨진 화면 대신 크기를 알려 주는 한 줄을 보여 주고, 크기가 바뀔 때마다 다시 잽니다.
어느 화면에서든 빠져나가는 길을 두고 `Ctrl+C`를 다른 뜻으로 쓰지 않습니다. 글을 입력하는 화면에서는 `q`를 종료 키로 쓰지 않습니다. 쓸 수 있는 키는 아래 줄이나 `?`로 보여 줍니다.
정상 종료·오류·Ctrl+C 등 모든 종료 경로에서 커서·대체 화면·raw 모드를 되돌립니다.
오류는 멈춤이 아니라 다음 행동이 있는 화면으로 보여 줍니다.

## 확인

실제로 실행해서 봅니다. 코드만 읽고 통과로 치지 않습니다.

- 색 있는 터미널과 `NO_COLOR=1`, 파이프(`| cat`) 출력을 비교합니다. 평문에서도 상태가 구분되는지 봅니다.
- `cmd > out.txt`로 stdout만 파이프했을 때 진행 줄이 파일에 섞이지 않는지 봅니다.
- `COLUMNS=60` 같은 좁은 폭과 긴 경로·긴 식별자·한글 이름으로 줄 맞춤과 자르기를 봅니다.
- 성공·주의·실패·빈 결과를 각각 한 번씩 내고 종료 코드를 `echo $?`로 봅니다.
- stdin을 닫은 상태(`< /dev/null`)에서 질문하는 명령이 기다리지 않고 끝나는지 봅니다.
- `--json` 출력이 성공과 실패 모두 유효한 JSON인지 봅니다.
- TUI는 정해진 크기에서 키 입력 순서와 화면을 고정해 비교하고, Ctrl+C로 끈 뒤 셸이 정상인지 봅니다.
- 출력 문구를 비교하는 기존 테스트가 있으면 실행합니다.

움직이는 출력이나 README 시연이 필요할 때만 터미널 녹화를 만듭니다.
