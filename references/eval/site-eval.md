# 사이트 평가하기

공개됐거나 공개를 앞둔 웹사이트·웹앱을 실제 브라우저로 살펴보고 판정 하나와 고칠 목록을 냅니다.
[읽기 전용 점검](../task-review.md)을 여러 페이지와 정해진 근거로 넓힌 흐름입니다.
두 규칙은 어디서나 지킵니다.

- 근거가 없는 발견은 버립니다.
- 판정은 확인한 범위만큼만 믿을 수 있습니다. 모드에 필요한 층을 실제 브라우저로 보지 못했으면 판정은 `확인 부족`입니다.

평가는 고치지 않습니다. 보고를 마치면 멈추고, 고치기는 사용자가 따로 부탁할 때만 합니다.

## 범위와 허락

| 대상 | 할 수 있는 일 |
|------|---------------|
| 사용자의 사이트, 점검을 허락받은 사이트 | 모든 모드와 층 |
| 남의 공개 사이트(경쟁사·참고·영업 대상) | 보기만 합니다. 페이지 읽기, 캡처, 크기 바꾸기, 올려 두기, 키보드 초점, 메뉴·접이식 열고 닫기, 읽기 전용 스크립트(axe-core를 페이지에 넣습니다). 폼 제출·로그인·부하·공격성 입력·시나리오 검사는 하지 않습니다 |

- 누구 사이트인지 모르면 한 번 묻고 보고서 머리에 적습니다.
- `robots.txt`의 금지 경로를 따르고 페이지 요청은 1초에 한 번 정도로 둡니다.
- 결제, 실제 사람에게 보내기, 되돌릴 수 없는 동작은 따로 허락받기 전에 하지 않습니다.
- 지어낸 테스트 자료만 씁니다. 실제 개인 정보를 넣지 않습니다.

## 모드

| 모드 | 쓰는 때 | 층 | 페이지 수 |
|------|---------|----|-----------|
| `quick` | 배포 전 빠른 확인 | 모든 페이지 L1·L5, 시작 페이지 차단 조건 | 3 |
| `site` | 소개·콘텐츠·랜딩·문서 사이트 | L1~L8, 보기만 하는 과제 따라가기 포함 | 25 |
| `app` | 로그인 뒤 도구·대시보드·폼이 많은 앱(사용자 소유·허락한 것만) | L1~L9 | 25 |

`quick`의 차단 조건 확인은 시작 페이지 한 곳에서 375·1440 배치 검사, axe, 성능, 콘솔·네트워크를 읽는 것입니다.
차단 조건에만 쓰며 L6~L8 점수를 만들지 않습니다.
사용자가 모드를 말하지 않으면 정하고 한 줄로 알립니다.

| 층 | 내용 | 문서 |
|----|------|------|
| L1 | 문구와 내용 | [내용·구조·전환·기술](content.md) |
| L2 | 구조·이동·과제 흐름 | [내용·구조·전환·기술](content.md), [과제 따라가기](walkthrough.md) |
| L3 | 전환 경로와 폼 | [내용·구조·전환·기술](content.md) |
| L4 | 시각 디자인 | [시각 디자인](visual.md) |
| L5 | 기술과 검색 노출 | [내용·구조·전환·기술](content.md) |
| L6 | 반응형 배치 | [반응형](responsive.md) |
| L7 | 접근성 | [접근성과 성능](a11y-perf.md) |
| L8 | 성능 | [접근성과 성능](a11y-perf.md) |
| L9 | 실제 조작과 동작 | [조작과 동작](interaction.md) |

발견에 붙일 원칙과 언어별 문구 점검은 [원칙과 언어](principles.md)에 있습니다.

### 층의 주인

결함 하나는 한 층의 발견 하나입니다. 두 검사가 같은 결함을 보더라도 한 번만 적습니다.

| 결함 | 주인 | 다시 적지 않는 곳 |
|------|------|-------------------|
| 글 대비 | L7 | L4 |
| 클릭 대상 크기 | L6 | L7(axe `target-size`는 L6 발견에 합칩니다) |
| 초점 보임, 키보드 순서 | L7 | L4 |
| `<title>`·meta·`alt` 누락이나 중복 | L5 | L7(axe가 `image-alt`로 잡으면 L7) |
| 첫 화면 밖으로 밀린 주된 버튼 | L3 | L6 |
| 글 넘침, 배치 무너짐 | L6 | L4 |

## 1. 짧은 확인

`quick`은 주소와 소유 여부만 묻습니다. 나머지는 기본값으로 두고 보고서에 적습니다.
`site`·`app`은 빠진 것만 한 번에 묻습니다. 대화에서 이미 답한 것은 다시 묻지 않습니다.

- 주소와 점검 허락
- 누가 어떤 기기로 얼마나 급하게 오는지
- 사이트가 이끌어야 할 주된 동작 하나
- 사용자가 이미 걱정하는 점
- 바라는 말투
- 내용의 언어와 지역 표기
- 마감
- `app`: 어느 로그인된 브라우저를 쓸지

답을 사용자 유형 한 줄(역할·기기·인내심·사전 지식)로 바꿔 보고서 맨 위에 둡니다.
모든 발견은 개발자가 아닌 그 사람의 자리에서 판단합니다.

## 2. 도구

`jstyle eval`이 기본입니다. 임시 브라우저로 페이지를 열고 크기별 캡처, 콘솔·네트워크, 배치·첫 화면·폼·스타일·axe·성능 검사를 한 번에 남깁니다.
선택지는 [도구](../tools.md#사이트-평가-자료)와 `jstyle eval --help`를 봅니다.

```text
node <skill>/bin/jstyle.mjs eval https://example.com https://example.com/pricing --mode site --funnel /pricing --keyboard --out .jstyle/eval-example-2026-11-08
```

이 도구는 보기만 합니다. `--keyboard`를 주면 시작·전환 페이지에서 Tab만 눌러 초점을 따라갑니다.
누르기·입력·제출이 필요한 L9와 Escape·메뉴 같은 나머지 키보드 확인은 환경의 브라우저 도구로 합니다.
로그인된 앱은 사용자의 기존 브라우저에 붙는 도구를 씁니다. 말없이 로그인하지 않은 새 브라우저로 바꾸지 않습니다.

다른 브라우저 도구를 쓸 때는 스킬 폴더의 `scripts/eval/*.js`를 JavaScript 실행 호출에 그대로 붙여 넣습니다.
각 파일은 JSON 문자열을 돌려주는 식 하나입니다. 일부 도구가 최상위 `await`를 다시 감싸며 결과를 잃기 때문에 쓰지 않았습니다.
먼저 캡처, 콘솔 읽기, 네트워크 목록, `document.title` 실행을 한 번씩 해 보고 실패하면 그것부터 고칩니다.

다음을 보고서 머리에 적습니다.

- 기기 흉내: 768px 미만에서는 터치·휴대폰 UA·DPR 2~3으로 휴대폰을 흉내 냅니다. 창 크기만 바꾸면 `hover: hover`가 남아 올려야만 열리는 메뉴를 보지 못합니다. 그럴 때는 확인 범위에 `너비만 바꿈`을 적습니다.
- 어두운 모드: 사이트에 있으면 `prefers-color-scheme: dark`로도 봅니다.

### 화면 크기

| 쓰임 | 크기 |
|------|------|
| 넓은 화면 첫 화면 | 1440 × 900 |
| 휴대폰 첫 화면 | 375 × 812 |
| 반응형 훑기 | 768px 미만은 높이 812, 이상은 900 |

첫 화면은 이 표의 높이 안을 뜻합니다. 처음 보이는 화면 캡처와 페이지 전체 캡처를 따로 남깁니다.
jstyle 캡처 도구의 기본 휴대폰 크기 390×844와 다릅니다. 평가에서는 이 표를 따릅니다.

| 스크립트 | 쓰는 층 |
|----------|---------|
| `layout-detect.js` | L6 넘침·잘림·무너짐·상자 밖으로 나간 글·클릭 대상(WCAG 간격 예외 포함)·작은 글자 |
| `fold-check.js` | L3·L2 첫 화면에 보이는 것, 주된 버튼 위치 |
| `style-audit.js` | L4 실제로 쓰인 글자 크기·색·모서리·그림자·간격·컨트롤 높이 |
| `form-audit.js` | L3 폼 이름표·입력 종류·자동 완성·뜻 없는 제출 버튼(읽기만) |
| `axe-run.js` | L7 위반과 사람이 봐야 할 항목 |
| `perf-capture.js` | L8 LCP·CLS·INP·TTFB |

`fold-check.js`는 맨 위로 올린 상태에서 실행합니다. 스크립트 결과는 단서이며 판정이 아닙니다.
화면 밖 요소, 눈에 덜 띄는 버튼, 폼 안내는 잘못 잡힐 수 있으니 캡처로 확인한 뒤 발견으로 올립니다.

`jstyle check`는 스타일 파일을 읽고 `style-audit.js`는 실제 화면에 적용된 값을 잽니다. 서로 대신하지 않습니다.
캡처 도구 `shoot`의 `lint`는 만드는 동안의 안내입니다. 평가의 배치 판단은 `layout-detect.js`를 기준으로 합니다.

### 브라우저가 없을 때

페이지를 글로 받아 봅니다. L1·L5는 모두, L2·L3는 일부만 볼 수 있습니다.
L2·L3는 `일부`, 나머지는 `보지 않음`으로 적고 판정은 `확인 부족`입니다.

### 작업 파일

정해진 곳이 없으면 `.jstyle/eval-<사이트>-<날짜>/`에 보고서 `report.md`, 캡처와 JSON을 함께 둡니다. [작업 파일](../workdir.md)을 따릅니다.
발견은 기억에 쌓아 두지 말고 찾는 대로 보고서에 적습니다.

## 3. 페이지 목록

판단하기 전에 페이지부터 적습니다.

1. 시작 페이지, 주 메뉴, 바닥 메뉴
2. 둘러보다 찾은 페이지
3. `/sitemap.xml`, `/robots.txt`, 일부러 없는 경로(404 화면), 가격·소개·약관·로그인 같은 흔한 경로
4. `app`: 모든 메뉴 구역을 걷습니다. 소스가 있으면 경로 정의를 읽습니다.

페이지 수 상한을 지킵니다. 같은 틀의 페이지(글·상품 상세)는 세 개만 보고 그렇게 했다고 적습니다.
페이지마다 경로·목적·주된 동작을 한 줄로 적고 전환 페이지(랜딩·가격·가입·결제)를 표시합니다.

## 4. 살펴보기

### 페이지마다

1. 열고 네트워크가 잠잠해질 때까지(또는 1.5초 정도) 기다린 뒤 콘솔과 네트워크를 읽습니다.
2. 넓은 화면 첫 화면과 전체 캡처, `fold-check.js` → L2·L3
3. 보이는 글, 링크 대상, 제목, 대체 글, head 정보를 읽습니다 → L1·L2·L3·L5
4. 폼이 있으면 `form-audit.js` → L3
5. 캡처와 `style-audit.js`로 시각 점검 → L4. `style-audit.js`는 시작 페이지와 틀마다 한 곳이면 됩니다.
6. 도구가 올려 두기를 할 수 있으면 주된 버튼과 메뉴 하나에 올려 두고 찍습니다 → L4 상태. 못 하면 확인 범위에 적으며 판정을 막지 않습니다.
7. 1440에서 `axe-run.js` → L7. 375 휴대폰 흉내에서 시작 페이지와 틀마다 한 곳을 다시 봅니다. 메뉴 버튼·고정 막대는 넓은 화면 DOM에 없습니다.
8. 여러 너비에서 `layout-detect.js`, 375에서 첫 화면 캡처와 `fold-check.js` → L6·L3
9. 어두운 모드가 있으면 1440·375에서 첫 화면 한 장씩 → L4
10. `app`만: [조작과 동작](interaction.md) → L9

### 평가마다 한 번

- 시작 페이지와 모든 전환 페이지에서 키보드 확인([접근성과 성능](a11y-perf.md)) → L7. Tab 순서와 초점 표시는 `jstyle eval --keyboard`로 남기고, Escape·메뉴는 환경의 브라우저 도구로 봅니다.
- 시작 페이지와 주된 전환 페이지에서 `perf-capture.js` → L8. 전환 페이지는 전환 기준, 나머지는 일반 기준으로 봅니다.
- 과제 따라가기: `site` 보기만 하는 과제 2~3개, `app` 끝까지 하는 과제 3~5개([과제 따라가기](walkthrough.md)) → L2·L3
- 상태: 빈 화면·불러오는 중·오류·성공·404가 있는지, 어떻게 보이는지 적습니다.

### 페이지 사이 비교

말투 차이, 되풀이된 문단, 서로 다른 수치, 같은 제품의 다른 이름, 같은 버튼 글이 다른 곳으로 가는 경우,
같은 컴포넌트가 페이지마다 다르게 생긴 경우를 찾습니다.

## 꼭 남길 근거

모드에 필요한 항목이 하나라도 빠지면 판정은 `확인 부족`이고 빠진 것을 적습니다.

| 항목 | quick | site | app |
|------|-------|------|-----|
| 콘솔·네트워크 읽기 | 모든 페이지 | 모든 페이지 | 모든 페이지와 모든 동작 뒤 |
| 첫 화면 캡처 | 넓은 화면은 모든 페이지, 휴대폰은 시작 페이지 | 넓은 화면·휴대폰, 모든 페이지 | 넓은 화면·휴대폰, 모든 페이지 |
| 전체 캡처 | 시작 페이지 | 모든 페이지 | 모든 페이지 |
| `layout-detect.js` | 시작 페이지 375·1440 | 모든 페이지, 기본 너비 | 모든 페이지, 기본 너비와 여러 패널 |
| `axe-run.js` | 시작 페이지 1440·375 | 모든 페이지 1440, 시작 페이지와 틀마다 한 곳 375 | `site`와 같고 열린 대화상자도 |
| `perf-capture.js` | 시작 페이지 | 시작과 주된 전환 페이지 | 시작과 주된 전환 페이지 |
| 키보드 Tab 기록 | — | 시작과 전환 페이지 | 시작과 전환 페이지, 열린 대화상자 |
| 과제 기록 | — | 과제 2~3개 | 과제 3~5개와 조작 기록 |

올려 두기 상태와 Escape 확인은 이 표에 없습니다. 하지 못하면 확인 범위에 적고 판정은 그대로 둡니다.

## 차단 조건

하나라도 걸리면 다른 결과와 상관없이 `실패`입니다. 아래 심각도는 낮출 수 없습니다.

| 조건 | 실패하는 때 | 심각도 |
|------|-------------|--------|
| 공개 페이지의 임시 글(라틴 채움 글, "TODO", 템플릿 기본 문구) | 1개 이상 | Critical |
| 사이트 자신의 주소에서 온 HTTP 5xx | 1개 이상 | Critical |
| 눈에 보이는 고장(빈 구역, 죽은 버튼, 실패한 요청)을 낸 자체 콘솔 오류 | 1개 이상 | Critical |
| 그 밖의 자체 콘솔 오류 | 1개 이상 | High |
| 4xx를 돌려주는 내부 링크 | 1개 이상 | High |
| 시험한 너비에서 가로 스크롤, `overflow-x: hidden`에 잘린 내용, 무너진 본문 열 | 1개 이상 | High |
| axe `critical` / `serious` | 1개 이상 | Critical / High |
| LCP·CLS·INP 기준 초과 | 일반 4.0초 / 0.25 / 500ms · 전환 2.5초 / 0.1 / 200ms | High |

페이지 목록을 만들며 일부러 보낸 요청은 빼고 셉니다. 없는 경로 확인과 다른 탐색 주소는 원래 4xx와 "Failed to load resource" 오류를 냅니다.
이것들은 잡음에 적고 차단 조건으로 세지 않습니다. 화면에 보인 결과(404 화면에 돌아갈 길이 없음 등)만 발견이 됩니다.

차단 조건이 아니며 묶어서 발견 하나로 적는 것:

- 콘솔 경고 → Low. 자체 코드이고 정해진 브라우저 버전에서 깨질 지원 중단 경고면 Medium
- 외부 콘솔 오류(분석·광고·확장·임베드) → Low, 출처별로 적음

자체 코드는 스크립트 주소가 사이트 자신의 주소이거나 사이트가 내려주는 묶음 파일인 경우입니다.
호출 기록이 불분명하면 자체 코드로 보고 그렇게 판단했다고 적습니다.

알려진 잡음은 `.jstyle/eval-config.json`으로 거릅니다. `jstyle eval --config`로 넘기거나 직접 볼 때 같은 기준을 씁니다.

```json
{
  "consoleIgnore": ["[Extension]", "Download the React DevTools"],
  "networkIgnore": ["/api/session-probe 401"],
  "axe": { "ignoreRules": ["region"], "ignorePages": ["/styleguide"] }
}
```

거르기 전과 뒤의 개수를 나란히 적습니다.

## 심각도

차단 조건의 심각도는 위 표로 고정합니다. 나머지는 Nielsen의 심각도 기준을 빌린 세 축으로 정합니다.

| 축 | 높은 쪽 | 낮은 쪽 |
|----|---------|---------|
| 영향 | 주된 동작을 끝낼 수 없거나 믿음을 잃습니다 | 겉모습뿐이며 눈치채지 못합니다 |
| 범위 | 전환 페이지나 사이트 전체에 쓰인 컴포넌트 | 거의 안 오는 페이지 하나 |
| 지속 | 올 때마다 막히고 돌아갈 길이 없습니다 | 한 번뿐이고 쉽게 피합니다 |

| 등급 | 흔한 조합 | 고칠 때 |
|------|-----------|---------|
| Critical | 주된 동작을 막거나 믿음을 깨며 범위가 넓음 | 공개 전, 지금 |
| High | 전환 페이지나 전체 컴포넌트의 눈에 띄는 결함·측정된 걸림 | 이번 주 |
| Medium | 눈에 띄지만 피할 길이 있거나 범위가 좁음 | 다음 작업 |
| Low | 마감 | 여유 있을 때 |

두 상한이 있습니다.

- 확신도가 `판단`(측정이나 관찰한 고장이 없는 취향)인 발견은 Medium까지입니다.
- 전환 경로 밖 페이지의 겉모습 문제는 Low까지입니다.

발견마다 `고침값`(바꿀 글·값을 정확히 줌) 또는 `제안`(구조를 바꿈)을 붙입니다.

## 발견 쓰는 법

```text
### F-07 · 휴대폰에서 가격 버튼이 첫 화면 밖에 있음
심각도: High · 층: L3 전환 · 종류: 제안 · 확신도: 측정
위치: /pricing 375×812 (/, /features도 같음)
사용자: 휴대폰으로 요금제를 비교하는 출근길 직장인, 한 손, 2분
원칙: H1 시스템 상태의 가시성 — 다음 단계가 보여야 누릅니다
근거: .jstyle/eval-acme-2026-11-08/pricing-375-fold.png · fold-check: "무료로 시작" top=1140, fold=812
관찰: "무료로 시작"이 세 문단 소개 뒤 1,140px 아래에 있습니다
기대: 요금제 카드와 버튼이 첫 화면에 보입니다
고침: 카드 위 소개 문단을 빼고 "무료로 시작"을 각 카드 안에 둡니다
```

| 확신도 | 뜻 |
|--------|----|
| `측정` | 스크립트·axe·네트워크·콘솔 값이 증명합니다 |
| `관찰` | 캡처나 기록한 과제 단계에서 보였습니다 |
| `판단` | 디자인·문구 의견입니다. 근거는 대상을 보여 줄 뿐 틀렸음을 증명하지 않습니다 |

- 원인별로 묶습니다. 결함 하나·컴포넌트 하나에 발견 하나이며 영향받는 페이지를 모두 `위치`에 적습니다. 25쪽에 걸친 공통 바닥글 문제도 발견 하나입니다.
- `원칙`에는 [원칙과 언어](principles.md)의 원칙이나 WCAG 기준을 적습니다. 왜 이 사람에게 해로운지 설명합니다.
- 시각 발견의 캡처는 도구가 허락하면 해당 요소를 자르거나 `shoot --mark`로 표시합니다. `shoot`은 대상마다 `page.png`로 저장하므로 발견마다 `--out <평가 폴더>/marks/F-07`처럼 폴더를 나눕니다.
- 문구 고침은 원문을 그대로 인용하고 사이트의 말투와 지역 표기로 바꿀 글을 줍니다.
- 동작 발견은 번호 붙은 재현 단계를 적고, 소스가 있으면 `파일:줄` 추정을 붙입니다. 확인하지 않은 줄 번호는 만들지 않습니다.
- 고침은 바로 커밋할 수 있을 만큼 구체적이어야 합니다. "개선을 고려하세요"는 고침이 아닙니다.
- 일부러 한 것일 수 있으면 사이트 주인에게 묻는 형태로 씁니다.

## 5. 판정과 점수

### 덜어내기

발견이 열 개를 넘으면 허락된 범위에서 새 점검자에게 목록만 주고 각 항목을 나누게 합니다.
`이 사이트`(이 사이트의 근거가 있고 이 사람에게 해당), `어디나`(어느 사이트에나 할 말이며 이 사이트의 근거가 없음), `중복`(다른 발견과 원인이 같음).
`어디나`는 버리고 `중복`은 원래 발견에 합친 뒤 개수를 적습니다. 만든 사람보다 처음 읽는 사람이 더 잘 덜어냅니다.
새 점검자를 쓸 수 없으면 직접 나누고 독립 점검은 하지 않았다고 적습니다.
차단 조건과 확신도 `측정`인 발견은 버리지 않습니다. 중복으로 합칠 수만 있습니다.

### 판정

이 차례로 정합니다.

1. 실패: Critical이나 High가 있거나 차단 조건에 걸렸습니다. 확인 범위가 모자라도 확인된 실패는 그대로이며 빠진 범위를 아래에 적습니다.
2. 확인 부족: 필요한 층을 건너뛰었거나, 글만 받아 봤거나, 필요한 근거가 빠졌거나, 로그인이 끊겼습니다.
3. 조건부 통과: Critical·High가 없고 Medium이 하나 이상입니다.
4. 통과: Critical·High·Medium이 없습니다. Low는 남을 수 있습니다.

보고서에는 한국어 판정 옆에 `Pass / Conditional Pass / Fail / Incomplete`를 함께 적어 다른 언어 보고서와 비교할 수 있게 합니다.

### 점수

층마다 `max(0, 10 − 3·Critical − 2·High − 1·Medium − 0.25·Low)`를 소수 한 자리로 냅니다. 묶은 발견은 한 번만 셉니다.
전체는 평가한 층의 평균이며 Critical이 있으면 4.0을 넘지 않습니다.
일부만 본 층은 점수를 내고 `일부`로 표시합니다. 보지 않은 층은 `—`와 까닭을 적습니다.

이 점수는 같은 사이트를 다시 볼 때 변화를 보는 숫자입니다. 결과물은 판정과 고칠 목록입니다.
[화면 살펴보기 안내](../reviewer-manual.md)의 1~10 디자인 점수와 다른 척도이며 섞거나 바꿔 쓰지 않습니다.
기존 화면을 다듬는 작업에서 점수를 매기지 않는다는 규칙은 그대로이고, 이 점수는 사용자가 평가를 부탁했을 때만 냅니다.

## 6. 보고서

[보고서 양식](report.md)을 따릅니다. 머리, 판정, 점수표, 요약, 효과와 품을 따진 고칠 것 다섯, 등급별 발견,
과제 결과, 페이지별 문구 고침, 반응형 바뀜, 스타일 목록, 상태, 단계별 계획, 남길 장점, 확인 범위와 한계, 맺음말입니다.

보고서는 사용자 언어로 씁니다. 대화에는 판정, 점수, 고칠 것 다섯, 파일 위치만 적습니다.

## 7. 고치고 다시 보기(사용자 코드만)

Critical·High를 고칠지 묻습니다. 받아들이면 [살펴보고 고치기](../extended/review-loop.md)의 고침 루프를 따릅니다.
고친 페이지·너비·동작만 다시 보고, 발견마다 고침·남음·새로 생김을 적은 뒤 점수와 판정을 바꿉니다.
